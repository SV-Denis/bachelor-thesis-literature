Relevance: Shows an example of EARS usage, provides further works to cite such as for CLEAR (Constrained Language Enhanced Approach to Requirements)

1. Ce problema..., 

Scaling Model-Based Development (driven by aviation standards DO-178C / DO-331) at Honeywell required high-quality textual requirements, as standard EARS alone still allows inconsistent domain terminology and vague action verbs (e.g., "modulate", "maintain").

Furthermore, refining high-level system requirements down into detailed software requirements requires expressing low-level behaviors (timing, priority, startup, default states) that make standard EARS templates overly complex

2. Cum se rezolva?, 

Domain Glossary & Constrained Action Language (restricting terminology so it is less ambiguous)


Constrained Language Enhanced Approach to Requirements (CLEAR). (augmented EARS):

	-reduces the need to refer to the actor

	-adds a higher level of specificity by augmenting the EARS syntax (priority, startup, default behaviours)


3. Exemple/use-cases, 

2-day workshop with Alistair Mavin, on-going training in Honeywell

results: overall very positive feedback, but hard to fully scale across the organization


4. Open questions?

Can we integrate EARS requirements with model-based development technologies such as SysML and Object Process Method
